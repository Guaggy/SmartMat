## Known limitations (shipped deliberately scoped down, not bugs)

- Multi-mat: each real mat (Serial/MQTT, keyed by mat_id) keeps its own tare, pressure calibration, orientation, typed mat size and ROI in `profiles/<mat_id>.json`. Remaining: simulated data has no profile (it inherits whatever is in memory at the same size); all ESP32-text mats on one port share that port's profile (mat_id = port name), and every USB Maxrays mat shares `maxrays-usb`; a profile saved at another grid size is ignored and overwritten at the next save. Switching or rotating resets the live analysis state.
- Multi-mat: the two-board hardware check (both boards stay connected and both show up in the device list) has not been run yet - test D in `../SETUP_AND_TEST.md`. Clear the old retained `smartmat/frame` topic on the broker once.
- Indices: every default reference value is an untuned placeholder - set real ones before reading anything into an index. Map indices and the cell signals are in the main Data dropdown (they need a complete pressure calibration; colour scale is always auto, no difference mode, no contours, hotspot outlines only on Calibrated pressure), but there are no sound/pop-up alerts (only the status-bar chip).
- Patient-detected indicator only means "enough cells loaded for long enough" - calibration weights also read as a patient. Not yet: timeline events, recording it.
- ROI: several named ROIs at once, saving ROIs to a file and an adjustable brush size are not built (the ROI is remembered per mat in its profile).
- Desktop-app web dashboard (the "Web UI" toggle): only the mat currently open in the desktop app is live there; the headless server shows every mat live. `http://<hostname>.local:8000` relies on Avahi/mDNS, which Raspberry Pi OS runs by default, but this has not been confirmed on the deployed Pi yet (the IP is shown beside it as a fallback). Both links in the About panel are clickable.
- The public website widget's "Live" mode is fully broken, not just a stale tunnel URL: `Website/smartmat-heatmap-widget.html` still points at the old `/data` address, which no longer exists after the web-dashboard rework (the new API is `/api/mats` and `/api/mats/<mat_id>`, shaped differently). See `Website/notes.md`.
- Mat size / load estimate: the "Estimated load" line is indicative only (force from calibrated pressure x cell area / 9.81, an engineering aid, not a weight measurement; the vendor says the mat is not for weighing). It needs the mat's physical sensing size entered once per mat ("Mat size...", or the preset); with the default linear pressure curve it is shown as "default curve, not calibrated". Cells are assumed uniform per mat (width / cols, height / rows), so edge margins or gaps between cells are not modelled.
- Packaging: the exe is unsigned, so Windows SmartScreen warns on first run (More info > Run anyway); a code-signing certificate would remove that and most antivirus flags. The one-file build trips antivirus more often and starts in 6-8 s. `settings.json` stores the MQTT password as plain text (chosen; revisit if the app is distributed widely). An open MQTT connection keeps its old broker until it reconnects.
- Maxrays: defaults are retuned from ONE seat take only (see "Retune assumptions" below); the config is global, so the resistive mat gets the same values. The 2 trailer bytes of each packet are ignored (checksum undocumented).
- Changing rotation or mirror while connected wipes that mat's tare and calibration (re-tare afterwards).
- ESP32: `mux_settling_delay_us` and the ADC calibration assumptions haven't been verified against real hardware yet (only tested in simulation so far).

## Maxrays MC266 datasheet (docs/mat_specs.pdf, vendor deck; the serial preset in `sources/serial_source.py` PROFILES)

- 20 x 20, USB Type C (CH340), 921600 baud, stream `A5 5A 01 96 ...`; vendor client shows 60.0 Hz. 5 V, max 200 mA.
- Range 800 Pa - 200 kPa (measured on a 1 cm2 circular contact). Repeatability +/-15 % (1.5 kg load), product consistency +/-20 %, about +/-10 % error at best. The vendor says it is NOT suitable for weighing, only for trends / presence - so the kg readout stays "indicative".
- Resistance is roughly a power law of pressure; conductance is roughly linear with pressure (so the default linear curve is a first guess only).
- Outer size 438 x 438 mm; the sensing grid is smaller. Preset sensing size (used when the mat's profile has no typed size; precedence profile file > preset > config MAT_*/CELL_*): **343 x 358 mm, cell pitch about 17.2 x 17.9 mm**, measured from the page-4 drawing: the 20 x 20 electrode grid is 20 x 22.32 px = 446 px square at 150 dpi, against the 438 mm outer box drawn 569 px wide and 546 px tall (the drawing is not equal-scale: the two 438 mm dimensions measure 1.299 and 1.247 px/mm), so 446/569*438 = 343 mm and 446/546*438 = 358 mm. Treat as +/-5 %; an equal-scale reading would give about 350 x 350. Measure the real mat and enter it under Mat size... to override.
- MQTT meta contract (`smartmat/<chip_id>/meta`, retained; `parse_meta` in `sources/mqtt_source.py`): exactly one of `<chip_id>,<rows>,<cols>` (value_max 1000, resistive firmware), `<chip_id>,<rows>,<cols>,<value_max>` or `<chip_id>,<rows>,<cols>,<value_max>,<model>,<width_mm>,<height_mm>` (S3 firmware, e.g. `a1b2c3d4e5f6,20,20,255,MC266,343,358`). Anything else (5, 6 or 8+ fields, bad numbers, model with characters other than letters/digits/`_`/`-`, non-positive sizes) is rejected. The model and size go through the same preset mechanism as the serial one and are never written into the profile; only a size typed under Mat size... is. Frames are not retained (the app ignores retained frames); `smartmat/<chip_id>/status` carries `online`/`offline` (S3 only).
- Frames: ~60 fps is averaged down to `SERIAL_TARGET_FPS` (default 10, 0 = off) before analysis; diagnostics show source and output rate. seat_take1 came in at 7.7 fps: each averaging window restarted at the next poll with a frame instead of where the last one was due, adding one 20 ms poll plus Windows sleep jitter to every window. Fixed (fixed window schedule); recordings made before the fix keep ~7.7 fps. Recording timestamps are the GUI's handling time (50 ms poll), so frame spacing jitters by up to ~50 ms either way.

### Retune assumptions (2026-10-16, from `samples/seat_take1.json` only)

- One 40 s take, 313 frames: ~4 s empty, sitting down at ~4.5 s, then seated with a visible shift/lean around 19-30 s. Nothing here is validated beyond this take; replay new takes with `python tools/replay_tune.py --file <take>.json` (add `--set` / `--sweep`) and `tests/test_retune.py`.
- Assumed: the default linear curve (255 counts = 50 kPa) is NOT trusted for absolute kPa, so hotspots are now relative: activate at 1.7 x / deactivate at 1.2 x the mean over loaded cells, with the old 20 / 15 kPa as floors (floors = about 102 / 77 counts on the default curve). A fraction of the loaded mean stays meaningful when cells saturate at 255 (up to 19 here); a load whose mean is above ~150 counts (1.7 x would exceed full scale) would show no new hotspot - not seen yet.
- Measured on the take (old -> new defaults): new hotspot ids after settling 5.8 -> 1.9 /min (the whole seat used to be one 290-cell "hotspot" splitting/merging at the edges); relief+resume events 26 -> 5 in 40 s; health-state cell changes 810 -> 165 /min (Noisy/Drifting at body-edge cells came from the 2 kPa contact threshold, Possible stuck from 0-count cells beside the body); idle: no contact, no hotspot, no noisy cell; one Major movement at sit-down.
- Contact threshold 2 -> 1 kPa (~5 counts, idle noise <= 1 count). Saturated still shows under the sitting bones; that is real (8-bit full scale), only its hold time went 5 -> 10 frames.
- Per-cell relief states (temporal.py) still change often at body-edge cells (~2700 cell changes/min); not retuned, nothing user-facing fires from it on this take.
- Data still wanted: 2 min sitting still; empty mat then a light object (book / 1-2 kg); lean left and right (held ~10 s each); standing up and leaving the mat empty for 30 s. Ideally one take on the resistive mat too, since the config is shared.
